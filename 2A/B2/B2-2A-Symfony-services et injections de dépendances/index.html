    Symfony : les services et le conteneur de services

    Synthèse de cours — BTS SIO 2e année (SLAM), d'après la documentation officielle Symfony (service_container).

    1. Pourquoi ce chapitre ?

    Dans une application Symfony, presque tout est fait par des services : le routage, la sécurité, l'envoi d'e-mails, la gestion des logs… Un service, c'est simplement un objet PHP qui fait un travail précis (un « outil ») : LoggerInterface, MailerInterface, un gestionnaire de messages, etc.

    Le conteneur de services (ou conteneur d'injection de dépendances) est l'objet qui sait construire ces objets et les connecter entre eux, et vous les fournit quand vous en avez besoin.

    🎯 Objectif pédagogique : comprendre l'injection de dépendances, savoir créer ses propres services et les utiliser dans un contrôleur.

    2. L'injection de dépendances (Dependency Injection)

    Le problème

    Prenons une classe qui crée elle-même son formateur :

    // src/Service/MessageGenerator.php
namespace App\Service;

use App\Formatter\TextFormatter;

class MessageGenerator
{
    public function getHappyMessage(): string
    {
        $messages = ['Bravo !', 'Excellent travail !', 'Continue comme ça !'];
        $formatter = new TextFormatter(); // ⚠️ créé DANS la classe
        return $formatter->format($messages[array_rand($messages)]);
    }
}

    Trois défauts majeurs :

    Défaut Conséquence
    Classe peu flexible Impossible de changer le formateur (ex. HTML au lieu de texte) sans modifier la classe
    Non configurable Tout le code qui l'utilise a exactement le même comportement
    Difficile à tester Impossible de remplacer TextFormatter par un « faux » objet pour les tests unitaires

    👉 Règle d'or : ne jamais créer ses dépendances avec new à l'intérieur d'une classe.

    Étape 1 : injecter par le constructeur

    La classe déclare ce dont elle a besoin, elle ne le crée plus :

    class MessageGenerator
{
    public function __construct(
        private TextFormatter $formatter, // la dépendance est injectée
    ) {
    }

    public function getHappyMessage(): string
    {
        // ... utilisation de $this->formatter->format(...)
    }
}

    C'est l'injection de dépendances : les objets reçoivent leurs dépendances de l'extérieur (ici via le constructeur).

    Étape 2 : dépendre d'une abstraction

    Pour être vraiment flexible, on type avec une interface plutôt qu'une classe concrète :

    // src/Formatter/FormatterInterface.php
namespace App\Formatter;

interface FormatterInterface
{
    public function format(string $message): string;
}

    class MessageGenerator
{
    public function __construct(
        private FormatterInterface $formatter, // n'importe quelle implémentation
    ) {
    }
}

    On peut alors injecter un TextFormatter, un HtmlFormatter… ou un objet factice (mock) pour les tests.

    Étude de cas : pourquoi l'interface rend les tests faciles (mock)

    Imaginons que MessageGenerator produise des messages et que nous voulions tester uniquement la logique de choix du message, sans dépendre du comportement réel du formateur.

    Cas 1 — sans interface (classe concrète injectée) : impossible à isoler

    class MessageGenerator
{
    public function __construct(private TextFormatter $formatter) {}

    public function getHappyMessage(): string
    {
        $messages = ['Bravo !', 'Excellent travail !', 'Continue comme ça !'];
        return $this->formatter->format($messages[array_rand($messages)]);
    }
}

    Pour tester, on est obligé d'instancier le vrai TextFormatter : le test teste en réalité deux classes à la fois. Si TextFormatter échoue (ou est lent, ou écrit dans un fichier…), le test de MessageGenerator échoue aussi, alors que sa propre logique est correcte.

    Cas 2 — avec interface : on injecte un « faux » formateur

    // tests/Service/MessageGeneratorTest.php
use App\Formatter\FormatterInterface;
use App\Service\MessageGenerator;

class UpperCaseFormatter implements FormatterInterface
{
    public function format(string $message): string
    {
        return mb_strtoupper($message);
    }
}

$generator = new MessageGenerator(new UpperCaseFormatter());
$message = $generator->getHappyMessage();

// on teste SA logique : le message sort bien en majuscules,
// preuve que MessageGenerator délègue bien au formateur
assert(mb_strtoupper($message) === $message);

    Ici le mock (UpperCaseFormatter, 5 lignes) est prévisible et sous notre contrôle : le test ne peut échouer que si MessageGenerator lui-même a un bug. En pratique, on utilise aussi les mocks générés par PHPUnit (createMock(FormatterInterface::class)), qui crée automatiquement un faux objet retournant la valeur qu'on décide :

    $formatter = $this->createMock(FormatterInterface::class);
$formatter->method('format')->willReturn('OK');

$generator = new MessageGenerator($formatter);
// le vrai TextFormatter n'est jamais instancié

    Ce que l'interface nous a apporté :

    Sans interface Avec interface
    Le test instancie le vrai formateur → test lent, fragile, couplé On injecte un faux prévisible → test rapide et isolé
    Un bug du formateur fait échouer le test de MessageGenerator Le test n'échoue que si la classe testée est en cause
    Impossible de tester les cas limites du formateur depuis le test On choisit la valeur de retour du faux (ex. chaîne vide, très longue…)

    💡 À retenir pour les tests : grâce à l'interface, on peut substituer n'importe quelle implémentation au moment du new dans le test — c'est exactement ce que le conteneur fait pour vous en production, avec l'implémentation choisie dans services.yaml.

    Étape 3 : qui crée tout ce monde ?

    Nouveau problème : quelqu'un doit instancier tous ces objets, dans le bon ordre, et recréer ce code à chaque évolution d'un constructeur. C'est le rôle du conteneur de services : il stocke la « recette » de chaque service, les construit seulement quand c'est nécessaire et une seule fois (on récupère toujours la même instance).

    3. Utiliser un service dans un contrôleur

    Il suffit de typer un argument du contrôleur : Symfony passe automatiquement le bon service.

    // src/Controller/ProductController.php
namespace App\Controller;

use Psr\Log\LoggerInterface;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Routing\Attribute\Route;

class ProductController extends AbstractController
{
    #[Route('/products')]
    public function list(LoggerInterface $logger): Response
    {
        $logger->info('Regarde, j\'utilise un service !');
        // ...
    }
}

    Commandes utiles pour découvrir les services disponibles :

    php bin/console debug:autowiring   # services « autowirables » (ceux qu'on peut typer)
php bin/console debug:container    # TOUS les services du conteneur, avec leur id

    ℹ️ Chaque service a un id unique dans le conteneur (ex. logger, router.default). Au quotidien, le type-hint suffit : pas besoin de connaître les ids.

    4. Créer ses propres services

    Bonne pratique : sortir la logique métier du contrôleur et la mettre dans une classe de service dédiée (ex. dans src/Service/). Elle devient réutilisable partout.

    #[Route('/products/new')]
public function new(MessageGenerator $messageGenerator): Response
{
    $message = $messageGenerator->getHappyMessage();
    $this->addFlash('success', $message);
    // ...
}

    Grâce au type-hint, le conteneur instancie MessageGenerator (et injecte lui-même son formateur). Points clés :

    • le service n'est construit que si on le demande (économie de mémoire) ;
    • il n'est construit qu'une seule fois : la même instance est renvoyée à chaque demande.

    5. La configuration par défaut : config/services.yaml

    Un nouveau projet Symfony démarre avec cette configuration :

    # config/services.yaml
services:
    _defaults:
        autowire: true      # injecte automatiquement les dépendances
        autoconfigure: true # enregistre automatiquement commands, subscribers...

    # rend toutes les classes de src/ disponibles comme services
    App\:
        resource: '../src/'
    • autowire: true : le conteneur lit les type-hints du constructeur et passe les bons services tout seul. Si ce n'est pas possible, une exception claire est levée. C'est ce qui fait « disparaître » le problème de création d'objets.
    • autoconfigure: true : le conteneur détecte le rôle de chaque service (commande console, subscriber Twig…) grâce aux interfaces implémentées, et l'intègre automatiquement (via des tags internes, ajoutés pour vous).
    • App\: resource: '../src/' : chaque classe de src/ peut être utilisée comme service, son id étant son nom complet de classe (App\Service\MessageGenerator). Les classes jamais utilisées sont retirées du conteneur final.

    Exclure des classes du conteneur

        App\:
        resource: '../src/'
        exclude:
            - '../src/Entity/'        # répertoire à exclure
            - '../src/SomeFile.php'   # fichier à exclure

    Ou directement dans la classe avec un attribut PHP :

    #[Exclude]
class SomeService { }

    6. Injecter autre chose que des services

    Tout ne s'autowire pas : paramètres, valeurs scalaires, etc. On utilise alors la section bind ou une configuration explicite.

    # config/services.yaml
services:
    _defaults:
        autowire: true
        autoconfigure: true
        bind:
            # tout service ayant un argument $adminEmail recevra cette valeur
            string $adminEmail: 'contact@monsite.fr'
            # un paramètre du conteneur (%...) :
            bool $debug: '%kernel.debug%'
    • Paramètres du conteneur : notés %nom_du_parametre% (ex. %kernel.debug%, %env(MAILER_DSN)%), ils stockent des valeurs de configuration.
    • Pour choisir une implémentation précise quand une interface a plusieurs implémentations, on définit un alias (FormatterInterface: '@App\Formatter\HtmlFormatter').

    7. Déboguer le conteneur

    Commande Rôle
    php bin/console debug:autowiring Liste des services autowirables (à typer dans vos arguments)
    php bin/console debug:container Tous les services et paramètres du conteneur
    php bin/console lint:container Vérifie la validité de la configuration

    💡 Astuce : debug:container nom_du_service affiche le détail complet d'un service (classe, arguments injectés, tags).

    8. À retenir (fiche bilan)

    1. Un service = un objet PHP réutilisable qui fait un travail précis ; le conteneur sait le construire et l'injecter.
    2. Injection de dépendances : les classes reçoivent leurs dépendances (constructeur) au lieu de les créer avec new.
    3. On dépend d'une interface, pas d'une classe concrète → flexibilité + tests faciles (mocks).
    4. Dans un contrôleur ou un service, typer l'argument suffit : public function list(LoggerInterface $logger).
    5. autowire + autoconfigure + resource: '../src/' : zéro configuration dans la plupart des cas.
    6. Le conteneur construit chaque service une seule fois, seulement si nécessaire.
    7. Pour injecter des valeurs simples : section bind et paramètres %...%.
    8. Commandes de débogage : debug:autowiring, debug:container, lint:container.
